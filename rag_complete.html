📚 RAG — Retrieval Augmented Generation

1. What is RAG?

🏫 School Kid Analogy: The Open-Book Exam

Imagine you're taking an exam. A normal LLM is like writing answers from memory only — sometimes you forget facts or make things up.

RAG is like an open-book exam — before answering each question, you LOOK UP the relevant page in your textbook, read it, and THEN write your answer based on what you just read.

Result: Fewer made-up answers. Grounded in real information.

That's the entire idea. Three steps: Retrieve relevant info → Augment the prompt with it → Generate a grounded answer.

2. Why Do We Need RAG?

❌ Without RAG (LLM alone)

• Makes up facts ("hallucination")
• Knowledge frozen at training date
• Can't access YOUR private data
• No way to verify claims

✅ With RAG

• Grounded in real documents
• Knowledge updates instantly (add new docs)
• Works with private/company data
• Can cite sources

🧑‍⚕️ Analogy: Doctor with vs without medical records

A doctor guessing from memory = LLM alone (might be wrong).

A doctor who checks your file before diagnosing = LLM with RAG (grounded in YOUR data).

3. The Full RAG Pipeline (7 Steps)

Click each layer to expand and see what happens inside:

① INGEST — Get documents into the system
Sources: PDFs, websites, APIs, databases. Clean HTML, remove junk. YOUR code: HackerNews, arXiv, dev.to, YouTube transcripts.
② CHUNK — Split documents into bite-sized pieces
Why? Because LLMs have limited context. You can't feed a 100-page PDF. You feed the 3 most relevant PARAGRAPHS. Strategies: fixed-size, semantic, parent-child.
③ EMBED — Convert text chunks into number arrays (vectors)
Each chunk becomes a point in 384-dimensional space. Similar meanings = nearby points. Model: sentence-transformers/all-MiniLM-L6-v2 (what YOU use).
④ INDEX — Store vectors in a searchable database
Vector database (Qdrant, Pinecone, Chroma) enables fast "find nearest neighbors" queries. YOUR setup: Qdrant Cloud with 5 collections.
⑤ RETRIEVE — Find the most relevant chunks for a query
Embed the user's question → search for nearest chunks → return top 3-5. Advanced: HyDE (embed a hypothetical answer instead of the question).
⑥ RERANK — Re-score results for better accuracy
Vector search is approximate. A cross-encoder sees query + document TOGETHER and gives a more accurate relevance score. Retrieve 20 → rerank → keep top 3.
⑦ GENERATE — LLM creates answer using retrieved context
Prompt: "Answer using ONLY the context below. If not in context, say 'I don't know.'" This grounding instruction prevents hallucination.

4. Chunking — Why & How

📖 Analogy: Highlighting a textbook

You don't highlight the ENTIRE book. You highlight KEY PASSAGES that answer your question. Chunking = deciding where to draw the boundaries of each "highlightable passage."

5. Embeddings — The Heart of RAG

🗺️ Analogy: A City Map of Meanings

Imagine a city where similar shops are on the SAME street. All bakeries on Baker Street, all bookstores on Reader Lane.

Embeddings create a "city map" for text — similar meanings live at nearby addresses (coordinates). When you search, you're finding the nearest shop to your location.

Key insight: "LLM agents" and "RAG pipeline" are CLOSE in this space even though they share few words. That's the power — meaning, not keywords.

6. Retrieval — Finding the Right Chunks

The vector DB returns chunks sorted by similarity score. Higher score = more relevant. But vector search is approximate — it can miss nuanced matches. That's where re-ranking helps.

7. Re-Ranking — The Precision Layer

🎯 Analogy: Job Interview Shortlisting

Vector search = scanning 1000 resumes by keyword match (fast but misses good candidates who used different words)

Re-ranking = reading the top 20 resumes CAREFULLY side-by-side with the job description (slow but accurate)

9. Advanced Patterns (What Gets You Hired)

🔮 HyDE — Hypothetical Document Embedding

Problem: Questions and answers live in DIFFERENT regions of embedding space. "How to improve accuracy?" is far from "Use cross-encoder re-ranking".

Solution: Generate a FAKE answer first → embed THAT → search with the fake answer's embedding. It lands CLOSER to real answers.

Analogy: Instead of shouting "WHERE IS THE BAKERY?" (question), you whisper "fresh bread, croissants, oven" (hypothetical answer) — and follow the smell to the bakery.

🔀 Hybrid Search — BM25 + Vector

BM25: Keyword matching (finds "Python" when you search "Python"). Fast, exact, misses synonyms.

Vector: Meaning matching (finds "Python" when you search "programming language"). Catches synonyms, misses exact terms.

Hybrid: Run BOTH → merge results → best of both worlds. Uses Reciprocal Rank Fusion to combine rankings.

👨‍👧 Parent-Child Chunking

Problem: Small chunks = precise search but lose context. Big chunks = good context but noisy search.

Solution: Store SMALL chunks (200 tokens) for searching. But when you find a match, return the PARENT chunk (800 tokens) for context.

Analogy: You search by CHAPTER TITLE (precise) but read the FULL CHAPTER (context).

🔄 Multi-Query Retrieval

Problem: One query might miss relevant docs that use different words.

Solution: Ask LLM to rephrase your question 3 different ways → search with ALL versions → merge results.

🧠 Quick Check — Did you understand?

Why does re-ranking improve results over vector search alone?

Because bi-encoders embed query and document SEPARATELY — they can miss nuanced relationships. Cross-encoders see the query + document TOGETHER as one input, understanding the relationship directly. It's like reading two things side-by-side vs remembering them separately.
