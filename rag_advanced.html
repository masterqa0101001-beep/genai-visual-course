1. The RAG Zoo — 6 Types You Must Know

Not all RAG is the same. Here are the evolution stages — from basic to cutting-edge:

① Naive RAG

YOUR CURRENT

Basic pipeline: chunk → embed → retrieve top-K → generate. No optimization. What tutorials teach.

Weakness: Bad chunks, no reranking, no evaluation.

② Advanced RAG

YOUR NEXT STEP

Adds: semantic chunking, cross-encoder reranking, HyDE, hybrid search, query expansion.

Key upgrade: Two-stage retrieval (fast then accurate).

③ Modular RAG

ARCHITECTURE

Each component is pluggable. Swap embedding model without changing retrieval. Swap vector DB without changing generation.

Key idea: Interface-based design. Any chunker, any embedder, any retriever.

④ Graph RAG (Microsoft)

2024-2025 TREND

Instead of flat chunks, build a KNOWLEDGE GRAPH (entities + relationships). Then traverse the graph to find context.

Best for: Complex domains with many interconnected entities (legal, medical, research).

⑤ Agentic RAG

YOUR ContentMind

An AGENT decides: "Do I need to retrieve? What query? From which collection? Is the result good enough or should I retry?"

Your code already does this! Trend ranker queries Qdrant, decides if topic is covered.

⑥ Multimodal RAG

EMERGING

Retrieve across text + images + audio. Use CLIP embeddings to search images with text queries. Your ContentMind partially does this (Pexels image search from text).

Coming: Video RAG, Audio RAG, cross-modal retrieval.

3. RAG Failure Modes — What Goes Wrong & How to Fix

💀 Failure 1: Hallucination Despite RAG COMMON

Symptom: LLM makes claims NOT present in retrieved context.

Root cause: Prompt doesn't enforce "use ONLY context." LLM falls back to training knowledge.

Fix: Add explicit instruction: "If the answer is not in the context below, say 'I don't have information about that.'" Also add: "Cite which chunk your answer comes from."

💀 Failure 2: Retrieved Wrong Chunks YOUR RISK

Symptom: Top-K results are about the right TOPIC but wrong ASPECT. Query about "deploying RAG" gets chunks about "what is RAG."

Root causes: (1) Chunks too broad (500 words covers multiple subtopics). (2) No reranking. (3) Bi-encoder misses nuance.

Fix: Smaller semantic chunks + cross-encoder reranking + HyDE for query expansion.

💀 Failure 3: Missing Relevant Chunks (Low Recall)

Symptom: The answer exists in your knowledge base but wasn't retrieved.

Root cause: Query uses different words than the document. "How to make it faster" vs doc says "latency optimization."

Fix: (1) HyDE. (2) Multi-query (rephrase 3 ways). (3) Hybrid search (BM25 catches exact terms vector misses).

💀 Failure 4: Chunk Cut Mid-Concept

Symptom: Retrieved chunk says "...which is why cross-encoders are better" but doesn't say better THAN WHAT or WHY.

Root cause: Fixed-size chunking split a paragraph in the middle.

Fix: Semantic chunking (split at meaning boundaries) OR parent-child chunking (retrieve small, return large).

💀 Failure 5: Context Poisoning

Symptom: One WRONG chunk in context makes the LLM produce incorrect answer (even with 4 correct chunks).

Root cause: Outdated document in your knowledge base. Or adversarial content injection.

Fix: (1) Metadata filtering (only retrieve docs updated after X date). (2) Source trust scoring. (3) Faithfulness check on output.

💀 Failure 6: Lost in the Middle

Symptom: LLM ignores chunks placed in the MIDDLE of a long context. Uses only first and last chunks.

Root cause: Attention mechanism naturally weights beginning and end more heavily.

Fix: (1) Fewer chunks (3 instead of 10). (2) Put most relevant chunk LAST (closest to generation). (3) Use "cite your sources" to force reading all.

4. Industry Implementations — How the Big Players Do RAG

🔍 Perplexity AI

Search + RAG

How: User query → web search (real-time) → extract chunks from top pages → rerank → generate with citations.

Key insight: They DON'T pre-index. They search the web LIVE per query. RAG from real-time web, not a static database.

Your ContentMind parallel: Your HackerNews/arXiv ingestion is similar — but theirs is real-time, yours is batched.

🤖 ChatGPT (Retrieval)

Agentic RAG

How: Model DECIDES if it needs to search (agentic). If yes → Bing search → extract → cite. If not → answer from training.

Key insight: The retrieval is OPTIONAL. Agent decides. This is Agentic RAG — exactly what your trend_ranker does (decides whether to call Qdrant).

💻 GitHub Copilot (Codebase RAG)

Code RAG

How: Embeds your entire codebase → when you type, retrieves relevant files/functions → injects as context → generates code that fits YOUR project.

Key insight: The "chunks" are functions and classes, not paragraphs. Chunking strategy is AST-based (code structure), not text-based.

📝 Notion AI

Workspace RAG

How: Embeds all your Notion pages → when you ask a question, retrieves from YOUR workspace → answers grounded in YOUR notes.

Key insight: Permission-aware RAG — only retrieves pages YOU have access to. Uses metadata filtering on user permissions.

🏥 Medical RAG (Hospitals)

Domain RAG

How: Medical literature + patient records → chunk by section (symptoms, treatments, studies) → retrieve with strict accuracy requirements.

Key insight: Hallucination is DANGEROUS here. They use triple-verification: retrieve → generate → fact-check against a second retrieval.

🎵 Spotify (Audio RAG — Emerging)

Multimodal

How: Embed podcast transcripts + audio features → search by topic OR by audio similarity → recommend related content.

Key insight: Multi-modal: text embeddings for content, audio embeddings for style/mood. Cross-modal retrieval.

5. Interview-Ready Answers

Q: "Design a RAG system for a customer support bot"

"I'd design it in three stages. Ingestion: Chunk support docs by FAQ structure (one chunk = one question+answer pair). Embed with a model optimized for Q&A retrieval like BGE or E5. Index in both vector store and BM25 for hybrid search.

Retrieval: At query time — hybrid BM25+vector search, cross-encoder reranking to get top 3 most relevant FAQ chunks. If confidence is below threshold, escalate to human.

Generation: Context-grounded prompt with citation requirement. Faithfulness check on output. If LLM hallucinates beyond context, return 'let me connect you with an agent' instead."

Q: "When would you use RAG vs Fine-tuning?"

"RAG when I need current/external knowledge that changes over time — company docs, product catalogs, recent events. Knowledge lives OUTSIDE the model.

Fine-tuning when I need the model to consistently BEHAVE differently — specific output format, domain vocabulary, style. The behavior is baked INTO the model.

Both together: Fine-tune for format compliance + RAG for factual grounding. Example: fine-tune to always output JSON medical reports, RAG to ground claims in patient records."

Q: "How do you evaluate RAG quality?"

"RAGAS framework with 4 metrics: Faithfulness (is the answer grounded in context? catches hallucination), Answer Relevancy (does it address the question?), Context Precision (are retrieved chunks relevant? catches noisy retrieval), Context Recall (did we miss relevant chunks?).

I maintain a golden test set of 30+ query-answer pairs. After any change to chunking, embedding model, or prompts, I run RAGAS to detect regression. If any metric drops >5%, the change is rolled back."

Q: "What is your chunking strategy and why?"

"I use semantic chunking — splitting at points where the embedding similarity between consecutive sentences drops below a threshold (mean - 1 std dev). This ensures each chunk is a COMPLETE thought rather than an arbitrary word boundary that cuts mid-sentence.

For production: I implement parent-child chunking — small chunks (200 tokens) for precise retrieval, but I return the parent chunk (800 tokens) to the LLM for richer context. This gives precision of small chunks with the completeness of large chunks."
