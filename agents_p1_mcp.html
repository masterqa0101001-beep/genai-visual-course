1. What MCP actually is

MCP is an open-source standard for connecting AI applications to external systems — data sources (files, DBs), tools (search, calculators), and workflows (specialized prompts). Before MCP, every app wired every tool with a custom integration (the "M×N problem"). MCP turns that into "build once, integrate everywhere."

WITHOUT MCP (M×N custom integrations) WITH MCP (M+N) App1 ─┐ ┌─ Tool1 App1 ─┐ ┌─ Tool1 App2 ─┼──┼─ Tool2 → App2 ─┼─[MCP]──┼─ Tool2 App3 ─┘ └─ Tool3 App3 ─┘ └─ Tool3 (every line = custom code) (one standard protocol)

3. The three server primitives

PrimitiveWhat it isExample
ToolsFunctions the model can call (actions)search_jobs, run_query
ResourcesData the model can read (context)a file, a DB row, a doc
PromptsReusable prompt templates/workflows"summarize-ticket" workflow
The distinction that impresses: Tools = do (model-controlled actions). Resources = know (app-controlled context). Most people only know "tools" — knowing all three + when to use each signals depth.

4. Transport: stdio vs HTTP+SSE

TransportUse when
stdioLocal server, same machine (CLI tools, local files). Simple, fast, no network.
HTTP + SSE (streamable)Remote server, over the network. Needs auth + network hardening.
YOUR work: your job_search MCP server exposes tools — that's exactly the Server role over a transport. In an interview: "MCP is function calling (structured tool defs) + a transport layer (stdio/HTTP) + discovery, so any MCP-aware agent can call my tools without custom glue."

5. MCP vs Function Calling vs A2A (know the difference)

ThingWhat it standardizes
Function callingHow ONE model calls a tool in ONE API call (the primitive)
MCPHow ANY app connects to ANY tool/data source (app ↔ tools)
A2A (P2)How agents talk to OTHER agents (agent ↔ agent)
Clean mental model: function calling is the atom, MCP is how you distribute tools to apps, A2A is how agents collaborate. They're complementary layers, not competitors.

6. ⚠️ MCP security (founder-critical)

An MCP server executes real actions — so it's a serious attack surface. The agent-security lessons apply directly:

  • Untrusted servers: connecting to a random MCP server = running its code paths. Vet them.
  • Tool poisoning: a malicious server can describe tools deceptively to manipulate the model (indirect injection via tool descriptions).
  • Auth on remote (HTTP) servers: stdio is local; the moment you go remote you need real auth + egress control.
  • Least privilege: an MCP tool that can delete or pay needs scoping + human-in-the-loop (ties to Excessive Agency, OWASP LLM06).

8. Q&A Drills

What problem does MCP solve?
The M×N integration problem — every app wiring every tool with custom code. MCP standardizes it to M+N: build a tool once as an MCP server and any MCP-aware agent can use it. USB-C for AI.
Tools vs resources vs prompts in MCP?
Tools are model-controlled actions (do something), resources are app-controlled context the model can read (know something), prompts are reusable templated workflows. Most people only know tools.
How is MCP different from function calling?
Function calling is the primitive — one model calling a tool in one API call. MCP is the distribution standard — how any app connects to any tool/data source over a transport (stdio or HTTP+SSE), with discovery. MCP uses function-calling-style structured defs under the hood.
What are the security risks of MCP?
An MCP server executes real actions, so: untrusted servers run arbitrary logic, tool descriptions can poison the model (indirect injection), remote HTTP servers need auth + egress control, and powerful tools need least-privilege scoping plus human gates.
