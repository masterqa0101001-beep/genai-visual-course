1. Self-RAG — The Model Becomes Its Own Quality Gate

🧑‍⚖️ Analogy: A Student Who Checks Their Own Work

Normal RAG = student looks up answer in textbook and writes it down (no self-checking).

Self-RAG = student (1) decides IF they need the textbook, (2) looks up relevant pages, (3) checks if the pages are actually helpful, (4) writes answer, (5) verifies answer matches the pages. Self-correcting at every step.

Why this matters: Normal RAG always retrieves (even when unnecessary). Self-RAG retrieves ONLY when needed, validates retrieved content, and self-checks its output. 3 quality gates built into one model.

YOUR connection: Your quality council is an EXTERNAL self-check. Self-RAG builds the check INTO the model itself. Same concept, different layer.

2. Corrective RAG (CRAG) — Self-Healing Retrieval

🏥 Analogy: Doctor With a Second Opinion Protocol

Normal doctor: checks your file, gives diagnosis. If the file is wrong → wrong diagnosis.

CRAG doctor: checks file → evaluates "is this file reliable?" → if NO → gets a SECOND OPINION (web search) → combines both → gives diagnosis.

The 3-State Retrieval Evaluator

After retrieving documents, CRAG evaluates them with a lightweight classifier:

CORRECT: Retrieved docs are relevant → proceed to generation normally.

INCORRECT: Retrieved docs are completely wrong → DISCARD them → trigger web search as fallback → use web results instead.

AMBIGUOUS: Some docs relevant, some not → trigger BOTH knowledge refinement (extract useful sentences) AND web search → combine.

The flow:

query → retrieve from KB → evaluate(retrieved_docs)
  if CORRECT → generate(query + docs)
  if INCORRECT → web_search(query) → generate(query + web_results)
  if AMBIGUOUS → refine(docs) + web_search(query) → generate(query + refined + web)

Why it's powerful: Most RAG systems blindly trust whatever the vector DB returns. CRAG says "wait, let me verify these are actually good results." If not → it has a FALLBACK. Production resilience.

3. RAPTOR — Hierarchical Summarization RAG

📚 Analogy: Book → Chapters → Section Summaries → Table of Contents

Normal RAG can answer "What did paragraph 3 say?" (specific). But it CAN'T answer "What is the overall theme?" (big picture) because no single chunk contains the full picture.

RAPTOR builds a TREE: raw chunks → cluster similar → summarize clusters → summarize summaries. Query matches at the RIGHT level of abstraction.

Query routing: "What specific API does the Qdrant client use?" → matches Layer 0 (raw chunk). "How does the RAG pipeline architecture work overall?" → matches Layer 2 (summary). The question's ABSTRACTION LEVEL determines which layer gets queried.

4. GraphRAG (Microsoft) — Knowledge Graphs + RAG

🕸️ Analogy: Wikipedia vs Google

Normal RAG (Google): Find the most relevant PAGE for your query. Works great for factual lookups.

GraphRAG (Wikipedia): Navigate CONNECTIONS between entities. "How is X related to Y through Z?" Normal RAG can't answer this because the relationship spans multiple disconnected chunks. A graph CONNECTS them.

How GraphRAG Works (3 Phases)

Phase 1 — Extract: LLM reads all documents → extracts ENTITIES (people, concepts, tools) and RELATIONSHIPS between them → builds a knowledge graph.

Phase 2 — Community Detection: Find clusters of strongly connected entities (communities). Summarize each community. Like finding "neighborhoods" in the graph.

Phase 3 — Query: "Global" queries (big picture) → use community summaries. "Local" queries (specific) → traverse graph edges from query entity to find related entities + their original text.

When to use: Complex domains with many interconnected entities (legal docs, medical records, research papers). NOT for simple FAQ retrieval — that's overkill.

Tools: Microsoft's GraphRAG (open source), Neo4j + LangChain integration, LazyGraphRAG (cheaper variant using community summaries only).

5. RAG vs Long Context — The 2026 Debate

⚡ THE #1 Interview Question in 2026: "Is RAG still needed with 1M token context windows?"

Gemini has 1M+ tokens. Claude has 200K. GPT-4 has 128K. If you can stuff ALL your docs into context... why bother with RAG?

When Long Context Wins

• Small corpus (<50K tokens total)
• Need to reason ACROSS the entire document
• Single-document analysis (summarize a report)
• Static content that rarely changes
• Simplicity matters more than cost

When RAG Still Wins

• Large corpus (millions of docs)
• Content changes frequently (news, tickets)
• Cost matters (1M tokens = expensive per query)
• Precision matters (attention degrades with length)
• Audit trail needed (cite which doc gave the answer)
• Privacy (only retrieve what's needed, not expose all)

🎯 The 2026 Answer: HYBRID (Retrieve then Long-Context Reason)

The default in 2026 is NOT pure RAG or pure long-context. It's:

Retrieve 50K-200K relevant tokens → then let the model REASON over them with full context.

Pure RAG: retrieves 3 chunks (1500 tokens) → may miss context. Pure long context: stuffs 1M tokens → attention degrades, expensive.

Hybrid: RAG selects the best 50K tokens → model sees enough context to reason deeply, but not so much that it gets lost. Best of both.

YOUR interview answer: "I don't see it as RAG vs long context — it's a per-feature decision. For dynamic, large-scale knowledge (my content pipeline's 5 sources), RAG is essential. For reasoning over a single report, I'd stuff it in context. Most production systems combine both: retrieve broadly, then reason deeply over the retrieved set."

6. Contextual Retrieval (Anthropic, 2024)

📋 Analogy: Sticky Note on Each Page

Imagine photocopying pages from a book. Without context, page 47 says "it increases by 15%" — but WHAT increases? You lost the chapter title.

Contextual Retrieval = before storing each chunk, prepend a "sticky note" explaining WHERE it came from: "This chunk is from Chapter 3: Revenue Metrics. The 'it' refers to Q4 revenue growth."

How It Works (Simple but 20-67% improvement!)
# Before embedding, prepend document context to each chunk
def add_context(chunk, full_document):
  context_prompt = f"""Here is the full document:
  {full_document[:2000]}
  
  Here is the chunk:
  {chunk}
  
  Write a short (2-3 sentence) context that explains
  what this chunk is about within the larger document."""
  
  context = llm(context_prompt)
  return f"{context}\n\n{chunk}" # prepend context!

Result: Each chunk becomes SELF-CONTAINED. When embedded, it captures not just the text but its ROLE in the larger document. Retrieval precision improves 20-67% (Anthropic's measurements).

Tradeoff: Requires one LLM call per chunk at ingestion time (not at query time). For 1000 chunks = 1000 LLM calls during bootstrap. Once done, queries are normal speed.

YOUR upgrade: In bootstrap_rag.py, before calling embed_and_chunk(), run this contextualization step. Cost: ~$1-5 one-time. Benefit: permanent precision improvement.

7. Context Compression — Remove Noise Before Generation

The Problem: Retrieved chunks contain irrelevant sentences

You retrieve a 500-token chunk. But only 100 tokens are relevant to the query. The other 400 tokens are noise that:

• Wastes context window budget
• Can distract the LLM (lost-in-the-middle amplified by noise)
• Costs money (tokens = $)

Solution — LLM Compressor:

# After retrieval, COMPRESS each chunk
def compress(query, chunk):
  prompt = f"""Extract ONLY the sentences from this text
  that are relevant to answering: {query}
  
  Text: {chunk}
  
  Relevant sentences only (or 'NONE' if nothing relevant):"""
  return llm(prompt) # returns just the relevant parts

# Pipeline: retrieve 10 chunks → compress each → pass 3 best to LLM
chunks = retrieve(query, k=10)
compressed = [compress(query, c) for c in chunks]
compressed = [c for c in compressed if c != "NONE"]
answer = generate(query, compressed[:3])

Tradeoff: Extra LLM call per chunk (adds latency). Use CHEAP model for compression (8B is fine for extraction). Alternative: use sentence-level reranking instead of full LLM compression.

9. RAG as a "Knowledge Runtime" (2026 Framing)

The Big Picture Shift in 2026

RAG is evolving from "retrieve-then-generate" into a comprehensive knowledge orchestration layer — like Kubernetes for knowledge. It manages:

• Retrieval (find the right information from multiple sources)
• Reasoning (decide what's relevant, what's conflicting, what's stale)
• Verification (fact-check, ground, cite)
• Governance (access control, audit trail, version tracking)
• Freshness (detect stale data, trigger re-ingestion)

When interviewers ask "what is RAG?" in 2026, they don't want "retrieve and generate." They want to hear you describe this FULL orchestration system.

10. Production RAG Anti-Patterns (What NOT to Do)

❌ Over-Retrieving (top-20 chunks)

Stuffing too many chunks causes lost-in-the-middle + token waste. Fix: Retrieve 20 → rerank → keep top 3. Quality over quantity.

❌ Mixing Embedding Models

Some chunks embedded with MiniLM, others with BGE. Vectors are INCOMPATIBLE. Fix: ONE model per collection. Re-embed everything if you switch.

❌ No Freshness Management

Index from 6 months ago. World has changed. Fix: Track ingested_at, alert when average age exceeds threshold, schedule re-ingestion.

❌ No Evaluation (Flying Blind)

Ship RAG without measuring quality. It degrades silently. Fix: Golden test set + weekly RAGAS metrics. Alert on regression.

❌ Word-Based Chunking (YOUR past)

Fixed 500-word splits cut mid-concept. Fix: Semantic chunking or at minimum sentence-boundary-aware splitting.

❌ No Citation/Attribution

User can't verify WHERE the answer came from. Fix: Include source metadata in prompt, require LLM to cite chunk IDs. Builds trust + enables debugging.

🎯 Master Interview Answer: "Walk me through how you'd build a production RAG system from scratch"

"I'd design it as a knowledge runtime with 5 layers:

1. Ingestion: Semantic chunking with contextual headers (Anthropic's technique) — each chunk is self-contained. Dual-indexed: dense vectors in Qdrant + BM25 sparse index for hybrid search.

2. Retrieval: Agentic routing decides SOURCE (vector DB, web, SQL). HyDE for query expansion. Hybrid search (BM25 + vector + reciprocal rank fusion). Retrieve 15-20 candidates.

3. Refinement: Cross-encoder reranking (top 20 → top 5). Context compression (remove irrelevant sentences). Corrective check: if retrieval confidence low → fallback to web search.

4. Generation: Context-grounded prompt with citation requirement. Temperature 0.2 for factual accuracy. Structured output (JSON with sources).

5. Evaluation: RAGAS metrics weekly (faithfulness >0.9, precision >0.8). Golden test set regression. LangFuse tracing for per-query debugging. Freshness alerts when content exceeds 30-day age."
