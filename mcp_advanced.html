1. JSON-RPC 2.0 — What Actually Flows on the Wire

MCP uses JSON-RPC 2.0. Every interaction is a request → response pair. Here's what the ACTUAL messages look like:

Step 1: Initialize (Client → Server handshake)
// Client sends initialization request
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-03-26",
    "capabilities": { "tools": {}, "resources": {} },
    "clientInfo": { "name": "kiro", "version": "1.0.0" }
  }
}

// Server responds with its capabilities
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2025-03-26",
    "capabilities": { "tools": { "listChanged": true } },
    "serverInfo": { "name": "job-search-mcp", "version": "1.0.0" }
  }
}

What's happening: Client says "hi, I support tools and resources." Server says "hi, I have tools available." Handshake done.

Step 2: List Tools (Client asks "what can you do?")
// Client requests available tools
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/list"
}

// Server responds with tool schemas (LLM reads these!)
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "tools": [
      {
        "name": "search_jobs",
        "description": "Search for job listings matching a query",
        "inputSchema": {
          "type": "object",
          "properties": {
            "query": { "type": "string", "description": "Search query" },
            "location": { "type": "string", "default": "India" }
          },
          "required": ["query"]
        }
      },
      {
        "name": "score_job",
        "description": "Score a job against candidate profile",
        "inputSchema": { ... }
      }
    ]
  }
}

Key insight: The LLM READS these descriptions and schemas. Tool poisoning attacks hide malicious text in the "description" field! This is where security matters.

Step 3: Call Tool (LLM decides → Client executes)
// Client calls a tool (LLM decided to search)
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "search_jobs",
    "arguments": { "query": "AI Engineer", "location": "Chennai" }
  }
}

// Server executes and returns result
{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "content": [
      { "type": "text", "text": "Found 3 jobs: 1) AI Engineer at TCS Chennai ₹25-35L..." }
    ]
  }
}

Flow: LLM says "I want to call search_jobs" → Host passes to Client → Client sends JSON-RPC to Server → Server executes function → Returns result → Client passes back to LLM → LLM uses result in response.

2. Complete MCP Server (Full Working Code)

Here's a COMPLETE server — read top to bottom, understand every line:

"""
Complete MCP Server: Job Search
Run: python job_search_server.py
Test: mcp dev job_search_server.py
"""
import json
from datetime import datetime
from mcp.server.fastmcp import FastMCP

# Create server instance (name shows up in tool discovery)
mcp = FastMCP("job-search", version="1.0.0")

# ──── TOOLS (functions the LLM can call) ────────────────────

@mcp.tool()
def search_jobs(query: str, location: str = "India", num_results: int = 5) -> str:
  """Search for job listings matching the query.
  Args:
    query: Job title or skills to search for
    location: City or country
    num_results: How many results to return (max 10)
  """
  # Your actual search logic here
  results = fetch_from_api(query, location, num_results)
  return json.dumps(results, indent=2)

@mcp.tool()
def score_job(title: str, description: str = "") -> str:
  """Score how well a job matches the candidate profile.
  Returns: JSON with score (0-100), tier, matched skills.
  """
  score = compute_score(title, description)
  return json.dumps({"score": score, "tier": get_tier(score)})

@mcp.tool()
def get_report() -> str:
  """Get the latest job search report (pre-built markdown)."""
  with open("data/job_report.md") as f:
    return f.read()

# ──── RESOURCES (data the LLM can read) ─────────────────────

@mcp.resource("profile://current")
def get_profile() -> str:
  """The current candidate profile for matching."""
  with open("profile.json") as f:
    return f.read()

@mcp.resource("results://latest")
def get_latest_results() -> str:
  """Most recent scored job results."""
  with open("data/scored_jobs.json") as f:
    return f.read()

# ──── PROMPTS (reusable interaction templates) ──────────────

@mcp.prompt()
def daily_search() -> str:
  """Run the full daily job search pipeline."""
  return (
    "Search for Applied AI Engineer jobs in Chennai and Bangalore. "
    "Score the top 5. Summarize the best matches with salary estimates."
  )

# ──── RUN ────────────────────────────────────────────────────
if __name__ == "__main__":
  mcp.run() # Default: stdio transport

Key patterns to notice:

1. @mcp.tool() — Each decorated function becomes a callable tool. The docstring IS what the LLM reads. Type hints define the JSON schema.

2. @mcp.resource() — Static data exposed via URI (like a read-only API endpoint). LLM can request this data.

3. @mcp.prompt() — Pre-built prompt templates. Like bookmarks for common interactions.

4. Return type is always str — Tools return text/JSON. The server serializes it into the JSON-RPC response.

3. Building an MCP Client (The Other Side)

You know how to build SERVERS. Here's how CLIENTS work — the code that CONNECTS to your server:

# MCP Client — connects to any MCP server and calls tools
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

async def run_client():
  # Define which server to connect to
  server_params = StdioServerParameters(
    command="python",
    args=["job_search_server.py"]
  )

  # Connect (starts server as subprocess)
  async with stdio_client(server_params) as (read, write):
    async with ClientSession(read, write) as session:
      # 1. Initialize handshake
      await session.initialize()

      # 2. Discover available tools
      tools = await session.list_tools()
      for tool in tools.tools:
        print(f"Tool: {tool.name} — {tool.description}")

      # 3. Call a tool
      result = await session.call_tool(
        "search_jobs",
        arguments={"query": "AI Engineer", "location": "Chennai"}
      )
      print(f"Result: {result.content[0].text}")

      # 4. Read a resource
      profile = await session.read_resource("profile://current")
      print(f"Profile: {profile.contents[0].text}")

import asyncio
asyncio.run(run_client())

What this shows: The client starts the server as a subprocess, handshakes, discovers tools dynamically (no hardcoding!), then calls tools by name with typed arguments. The client is what Claude Desktop, Kiro, or Cursor run internally.

4. Configuration — Registering Servers with Hosts

Kiro (your IDE) — .kiro/settings/mcp.json
{
  "mcpServers": {
    "job-search": {
      "command": "python",
      "args": ["C:/path/to/job_search_server.py"],
      "env": { "GROQ_API_KEY": "your_key" },
      "disabled": false,
      "autoApprove": ["search_jobs", "get_report"]
    }
  }
}

"command" = what executable to run. "args" = path to your server. "autoApprove" = tools that don't need human confirmation.

Claude Desktop — claude_desktop_config.json
// Location: %APPDATA%/Claude/claude_desktop_config.json (Windows)
{
  "mcpServers": {
    "job-search": {
      "command": "python",
      "args": ["C:/Users/Hemanth/.../job_search_mcp.py"]
    },
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "C:/allowed/path"]
    }
  }
}

Same format. Multiple servers can be listed. Claude starts each as a subprocess when it launches.

Remote server (HTTP/SSE — for cloud deployment)
// For remote MCP servers deployed to Cloud Run etc.
{
  "mcpServers": {
    "job-search-remote": {
      "url": "https://job-search-mcp-xxx.run.app/sse",
      "headers": { "Authorization": "Bearer your_api_key" }
    }
  }
}

This is the future pattern: Deploy your MCP server to the cloud → connect from anywhere. YOUR server with HTTP transport + Cloud Run = accessible from any MCP client globally.

5. Error Handling Patterns

What happens when a tool FAILS
// Server returns error (tool threw an exception)
{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "content": [{ "type": "text", "text": "Error: API rate limited. Try again in 30s." }],
    "isError": true
  }
}

The "isError: true" flag tells the LLM "this tool failed." The LLM can then decide: retry? use a different tool? tell the user? This is how agents handle failures gracefully.

Production error handling in YOUR server
@mcp.tool()
def search_jobs(query: str, location: str = "India") -> str:
  """Search for jobs."""
  try:
    results = fetch_from_api(query, location)
    if not results:
      return "No jobs found for this query. Try broader terms."
    return json.dumps(results)
  except RateLimitError:
    return "Rate limited. Please wait 30 seconds and retry."
  except TimeoutError:
    return "Search timed out. The job API may be down."
  except Exception as e:
    return f"Unexpected error: {str(e)}"

Pattern: Never let exceptions crash the server. Always return a human-readable error string. The LLM reads this and adapts.

6. Testing MCP Servers

MCP Inspector (Built-in)

Command: mcp dev your_server.py
Opens a web UI where you can: see all tools listed, call them manually with test args, inspect request/response JSON, verify schemas. USE THIS FIRST.

Unit Testing (pytest)

def test_search_returns_results():
  result = search_jobs("AI Engineer", "Chennai")
  data = json.loads(result)
  assert len(data) > 0
  assert "title" in data[0]

Test the functions DIRECTLY (not through MCP protocol). Fast, no server needed.

Integration Testing (full protocol)

async def test_mcp_flow():
  client = await connect_to_server("server.py")
  tools = await client.list_tools()
  assert "search_jobs" in [t.name for t in tools]
  result = await client.call_tool("search_jobs", {"query": "AI"})
  assert not result.isError

Tests the FULL protocol flow. Catches: broken schemas, serialization bugs, transport issues.
