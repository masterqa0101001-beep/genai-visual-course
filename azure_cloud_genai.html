1 · LLM calls — Azure OpenAI

The one mental model: deployment name ≠ model name

In Azure you don't call gpt-4o directly. You deploy a model into your resource and give the deployment a name (e.g. gpt-4o-prod). Your code calls the deployment name. This lets you swap the underlying model version, set per-deployment quotas, and apply per-deployment RBAC — without changing client code.

Public OpenAI Azure OpenAI ──────────── ───────────── api.openai.com https://<your-resource>.openai.azure.com/ model="gpt-4o" model="gpt-4o-prod" ← YOUR deployment name key in header Entra ID token (keyless) ← recommended data leaves your tenant data stays in your tenant / chosen region

The right way to authenticate: keyless (Managed Identity)

Microsoft's own guidance: prefer keyless auth via Microsoft Entra ID. A key that is never issued can never be leaked into a repo, image layer, or log line. (Content rephrased from Microsoft Learn for licensing compliance.)

# pip install openai azure-identity
from azure.identity import DefaultAzureCredential, get_bearer_token_provider
from openai import AzureOpenAI

# On Azure compute this resolves to the attached Managed Identity.
# Locally it falls back to your `az login` session — identical code, no secret.
token_provider = get_bearer_token_provider(
    DefaultAzureCredential(),
    "https://cognitiveservices.azure.com/.default",
)

client = AzureOpenAI(
    azure_endpoint="https://my-openai-weu.openai.azure.com/",
    azure_ad_token_provider=token_provider,   # ← no api_key
    api_version="2024-10-21",
)

resp = client.chat.completions.create(
    model="gpt-4o-prod",   # deployment name, NOT model name
    messages=[{"role": "user", "content": "Summarize this incident report."}],
    temperature=0.2,       # low temp for factual/banking work
)
print(resp.choices[0].message.content)

Embeddings on Azure (for RAG)

emb = client.embeddings.create(
    model="text-embedding-3-large",   # deployment name of your embedding model
    input=["What is our refund policy?"],
)
vector = emb.data[0].embedding   # 3072-dim vector → store in Azure AI Search
Interview one-liner: "Azure OpenAI is the same models as OpenAI, wrapped for the enterprise: data stays in your tenant/region, Entra ID identity instead of shared keys, built-in content filtering, and per-deployment RBAC and quotas."

2 · Storage — Blob, Cosmos DB, Key Vault

Azure Blob Storage — the raw document lake

Where your source documents (PDFs, transcripts, code) live before ingestion. Azure AI Search can index Blob directly, and Blob is where you keep fine-tuning training sets behind tight RBAC.

from azure.identity import DefaultAzureCredential
from azure.storage.blob import BlobServiceClient

svc = BlobServiceClient(
    account_url="https://mystorage.blob.core.windows.net",
    credential=DefaultAzureCredential(),      # keyless again
)
container = svc.get_container_client("source-docs")
with open("policy.pdf", "rb") as f:
    container.upload_blob(name="policy.pdf", data=f, overwrite=True)

Azure Cosmos DB — state, chat history, and vectors

Your operational database: conversation history, user metadata, agent state / checkpoints. Cosmos DB now also supports native vector search, so for smaller workloads you can store embeddings alongside your app data instead of a separate search service.

Design call: Use Azure AI Search when retrieval quality/scale is the priority (hybrid + semantic ranker). Use Cosmos DB vector when you want vectors co-located with transactional data and simpler ops. Being able to justify this trade-off is a senior signal.

Azure Key Vault — where secrets go (if you must have them)

Best practice is keyless. When a secret is unavoidable (a third-party API key, a DB connection string), it lives in Key Vault and is fetched at runtime via Managed Identity — never in .env in production.

from azure.identity import DefaultAzureCredential
from azure.keyvault.secrets import SecretClient

kv = SecretClient(
    vault_url="https://my-kv.vault.azure.net",
    credential=DefaultAzureCredential(),
)
groq_key = kv.get_secret("GROQ-API-KEY").value
BNP tie-in: In your ContentMind project you load keys from a .env file. The enterprise upgrade story to tell: "In production I'd move those to Key Vault fetched via Managed Identity, so no secret ever sits on disk or in the image." That shows you understand the gap between a demo and a bank deployment.

3 · Vector search — Azure AI Search

Why it's more than a vector DB

Azure AI Search runs keyword (BM25) and vector queries in parallel, merges them with Reciprocal Rank Fusion (RRF), then optionally re-scores the top results with a semantic ranker (an L2 cross-encoder-style reranker). That's the exact hybrid-search pattern you already built by hand with Qdrant — Azure gives it to you as a managed feature. (Facts from Microsoft Learn; rephrased for compliance.)

Query "refund policy error 429" │ ├──────────────┬──────────────────┐ ▼ ▼ Keyword (BM25) Vector (kNN) ← run in PARALLEL catches "429", catches meaning exact codes of "refund policy" │ │ └──────► RRF fusion ◄──────┘ score = Σ 1/(k + rank) │ ▼ Semantic ranker (L2) ← re-scores top N for relevance │ ▼ Top-k grounded chunks → LLM

Creating a hybrid query

from azure.identity import DefaultAzureCredential
from azure.search.documents import SearchClient
from azure.search.documents.models import VectorizableTextQuery

search = SearchClient(
    endpoint="https://my-search.search.windows.net",
    index_name="documents",
    credential=DefaultAzureCredential(),
)

results = search.search(
    search_text="refund policy error 429",          # keyword / BM25 leg
    vector_queries=[VectorizableTextQuery(
        text="refund policy error 429",              # vector leg (auto-embedded)
        k_nearest_neighbors=5,
        fields="content_vector",
    )],
    query_type="semantic",                            # turn on semantic ranker
    semantic_configuration_name="default",
    select=["title", "content", "source"],
    top=5,
)
for r in results:
    print(r["@search.reranker_score"], r["title"])

Integrated vectorization — no manual embedding pipeline

Azure AI Search can chunk and embed your documents automatically at ingestion time (calling your Azure OpenAI embedding deployment) and re-embed the query at search time. This removes the hand-written chunk→embed→upsert code you wrote in bootstrap_rag.py — the service does it.

When to use it: Integrated vectorization = less code, fewer moving parts, good default for enterprise. Custom pipeline (like your Qdrant one) = more control over chunking/embeddings. Name both and state the trade-off.
BNP tie-in: "I've implemented hybrid search from scratch — BM25 sparse vectors fused with dense vectors via RRF on Qdrant. Azure AI Search productionizes exactly that pattern with a managed semantic ranker on top, so I understand both the internals and the managed service." That's a killer answer.

4 · Managing requests — APIM gateway, quotas, retries

The problem Azure OpenAI alone can't solve

A bare Azure OpenAI deployment has no concept of per-consumer quotas. Every app sharing a deployment competes for the same tokens-per-minute (TPM), and one runaway retry loop starves everyone. The fix is the AI gateway pattern: put Azure API Management (APIM) in front.

App A ─┐ App B ─┼──► Azure API Management ──► Azure OpenAI deployment App C ─┘ │ ├─ per-consumer token quota (429 when exceeded) ├─ emit token metrics (chargeback + anomaly alerts) ├─ central logging of every request └─ authenticates to backend with ITS OWN managed identity

APIM policy: per-consumer token budget

<inbound>
  <!-- Per-consumer token budget: 429 on rate, 403 on quota -->
  <azure-openai-token-limit
      counter-key="@(context.Subscription.Id)"
      tokens-per-minute="5000"
      estimate-prompt-tokens="true"
      remaining-tokens-header-name="x-remaining-tokens" />

  <!-- Emit per-consumer token metrics for chargeback / anomaly detection -->
  <azure-openai-emit-token-metric namespace="openai">
    <dimension name="Subscription ID" value="@(context.Subscription.Id)" />
  </azure-openai-emit-token-metric>

  <!-- Gateway authenticates to the backend once, with a managed identity -->
  <authentication-managed-identity resource="https://cognitiveservices.azure.com" />
</inbound>

Client-side resilience: rate limits, retries, timeouts

Even with a gateway, your client must handle 429s and transient failures gracefully.

import time, random
from openai import RateLimitError, APITimeoutError

def call_with_backoff(client, **kwargs):
    for attempt in range(5):
        try:
            return client.chat.completions.create(timeout=30, **kwargs)
        except RateLimitError:                     # 429 → honor Retry-After / backoff
            wait = (2 ** attempt) + random.random()  # exponential + jitter
            time.sleep(wait)
        except APITimeoutError:
            if attempt == 4:
                raise
    raise RuntimeError("Exhausted retries")
BNP tie-in: Your failure taxonomy in tracer.py already separates LLM_RATE_LIMIT, LLM_TIMEOUT, and TOOL_TIMEOUT. Say: "I classify failures by type so recovery is targeted — a 429 gets backoff, a timeout gets a retry with a circuit breaker, and I emit token metrics per consumer so a runaway loop shows up as a spend anomaly, not an outage." That maps 1:1 to the APIM pattern.

5 · Security — the 5 layers a bank cares about

This is the section that wins a banking interview. The default posture of a new Azure OpenAI resource is permissive — key auth enabled, public endpoint reachable. Hardening = flipping defaults, in this order.

Real-world stakes: CVE-2025-53767 was a server-side request forgery in Azure OpenAI that let an attacker hit the internal metadata endpoint and steal the resource's managed-identity token — which becomes tenant-wide compromise if that identity is over-privileged. Lesson: least privilege on the identity is not optional.

Layer 1 — Identity: turn off the keys

  • Set disableLocalAuth: true → the shared-key path disappears.
  • Use Microsoft Entra ID + Managed Identity for all calls (keyless).
  • Assign the least-privilege data-plane role: Cognitive Services OpenAI User (inference only) — scoped to the individual account, never the subscription.
  • Enforce across the estate with Azure Policy (start in Audit mode, then Deny).

Layer 2 — Network: take the endpoint off the internet

  • publicNetworkAccess: Disabled + networkAcls.defaultAction: Deny.
  • Add a Private Endpoint inside your VNet; requires a customSubDomainName.
  • Register the private DNS zone privatelink.openai.azure.com (the #1 thing people get wrong — A record lands in the wrong zone and resolution fails).

Layer 3 — Gateway: quotas + central logging (APIM, see §4)

Layer 4 — Data & compliance

SettingWhy it matters for a bank
Deployment type: Regional / DataZone vs GlobalDecides data residency. Regional = stays in one region; DataZone = stays in a geography (EU/US). This is your answer to "where is our data processed?"
Abuse monitoring / content loggingBy default Microsoft may retain flagged prompts for review. Regulated customers can apply for modified abuse monitoring exemptions. Don't promise "nothing is retained" without checking.
Customer-Managed Keys (CMK) in Key VaultEncryption at rest under your key — a common compliance requirement.
Content filters + Prompt ShieldsFilters cover hate/sexual/violence/self-harm. Prompt Shields target jailbreaks and indirect prompt injection — critical for RAG, where untrusted text arrives inside a retrieved document.

Layer 5 — Detection: prove you'd notice

Route diagnostic logs to Log Analytics and write the alert before you need it. The highest-value detection is a token-spend anomaly — because stolen credentials and a broken retry loop look identical on the bill.

// KQL: callers whose hourly volume is far above their own baseline
AzureDiagnostics
| where ResourceProvider == "MICROSOFT.COGNITIVESERVICES"
| summarize calls = count() by bin(TimeGenerated, 1h), identity_claim_appid_g
// ... join against a per-identity baseline, flag calls > baseline * 5
Hardening order (identity → network → gateway → data → detection): 1. disableLocalAuth = true ← removes the #1 leak path 2. publicNetworkAccess = Disabled ← removes remote attackers 3. APIM in front ← quotas + logging the resource lacks 4. Regional deployment + CMK + filters← residency, encryption, safety 5. Diagnostic logs + spend alert ← covers what you haven't fixed yet
BNP tie-in (say this): "For a bank I'd deploy Azure OpenAI keyless with Entra managed identity and the OpenAI User role scoped to the account, behind a private endpoint with public access disabled, fronted by APIM for per-consumer token quotas and central logging, on a Regional deployment for data residency, with content filters + Prompt Shields for injection, and diagnostic logs to Log Analytics with a spend-anomaly alert." — That single paragraph demonstrates enterprise maturity most candidates can't.

7 · Interview questions

Q: "How is Azure OpenAI different from calling OpenAI directly?"
A: Same models, enterprise wrapper. Data stays in your tenant and chosen region (residency), you authenticate with Entra ID identities instead of shared keys, you get per-deployment RBAC and quotas, built-in content filtering and Prompt Shields, private networking, and full audit logging. You call a deployment name, not a model name.
Q: "How would you do vector search on Azure?"
A: Azure AI Search. It runs BM25 keyword and vector kNN in parallel, fuses with Reciprocal Rank Fusion, then re-scores top results with a semantic ranker. Integrated vectorization can chunk and embed automatically at ingest and query time. For smaller workloads, Cosmos DB now has native vector search co-located with app data.
Q: "How do you secure a GenAI app in a bank on Azure?"
A: Five layers — (1) identity: keyless via Entra managed identity, least-privilege OpenAI User role scoped to the account; (2) network: private endpoint, public access disabled; (3) gateway: APIM for per-consumer token quotas and central logging; (4) data: Regional/DataZone deployment for residency, CMK encryption, content filters + Prompt Shields; (5) detection: diagnostic logs to Log Analytics with a token-spend anomaly alert.
Q: "How do you manage requests / prevent one team starving others?"
A: Azure OpenAI has no per-consumer quota on its own, so I put APIM in front with the azure-openai-token-limit policy — each consumer gets a TPM budget, exceeding it returns 429. APIM also emits per-consumer token metrics so I can alert on anomalous spend, and it authenticates to the backend with its own managed identity. Client side, I add exponential backoff with jitter on 429/timeout plus a circuit breaker.
Q: "What's the risk of an over-privileged managed identity?"
A: If the identity attached to the resource has Owner/Contributor at subscription scope, a service-side flaw (like CVE-2025-53767's SSRF against the metadata endpoint) that leaks its token becomes tenant-wide compromise. Mitigation: assign only the data-plane role you need (OpenAI User), scoped to the individual account — never the subscription.
Q: "How do you defend RAG against prompt injection on Azure?"
A: Enable Prompt Shields (they specifically target indirect/injected instructions arriving inside retrieved documents), treat all retrieved content as untrusted, separate system vs user content, validate/limit tool permissions, and filter outputs. Injection through a poisoned document is the RAG-specific threat, so the shield at the retrieval boundary matters most.
