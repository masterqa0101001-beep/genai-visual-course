📊 P1 — Evaluation & Observability

How you know an agent actually works — and keep knowing in production. Explicitly demanded in 2026 job postings. This is YOUR edge (QA × AI).

⭐ THE FOUNDER TRUTH

"Agents are non-deterministic, so 'it worked once' means nothing. You can't ship what you can't measure. Evaluation tells you if it works before you ship; observability tells you if it's still working after. No evals = no business."

PART A — EVALUATION

1. Why agent eval is hard

Traditional software: input → deterministic output → assert equals. Agents: same input → different outputs, multi-step trajectories, "correct" is fuzzy. You evaluate distributions and trajectories, not exact matches.

2. The levels of agent evaluation

LevelQuestion it answersMethod
Final outputWas the answer good?LLM-as-judge, reference comparison, rubric
TrajectoryDid it take sensible steps / call the right tools?step/tool-call trace eval
Task successDid it accomplish the goal?pass/fail on a goal checker
ComponentIs retrieval / a tool good in isolation?RAGAS (faithfulness, relevance), unit tests

3. LLM-as-Judge (the workhorse)

Use a strong model to score outputs against a rubric. Powerful but biased — handle the pitfalls:

Judge pitfalls: position bias (prefers first answer), verbosity bias (prefers longer), self-preference (prefers its own style), and variance (same input, different score). Fixes: randomize order, fix the rubric tightly, average multiple runs, calibrate against human labels.
# LLM-as-judge sketch
judge_prompt = """Score 1-5 on FAITHFULNESS to the source.
5 = fully supported, 1 = fabricated. Return JSON: {"score":N,"reason":"..."}
SOURCE: {source}
ANSWER: {answer}"""
# run 3x, average, log score + reason for audit

4. Datasets & regression suites

  • Golden dataset: curated input→expected pairs that define "good."
  • Regression suite: run it on every prompt/model change so you catch quality drops before shipping.
  • Offline vs online: offline = batch on a dataset pre-ship; online = sample live traffic post-ship.
Tools: LangSmith, Ragas, DeepEval, promptfoo.
YOUR work: your evaluation/evaluators.py is this layer. Add a golden dataset + a regression run tied to prompt changes and you've got a real eval harness — exactly what 2026 JDs ask for.

PART B — OBSERVABILITY

5. What to trace

RUN (trace) └─ Agent step 1 (span) ├─ LLM call → tokens, cost, latency, prompt, response ├─ Tool call → name, args, result, duration └─ decision → which tool, why └─ Agent step 2 (span) ... └─ RUN summary → total tokens, total cost, success, failures
MetricWhy it matters
Tokens + cost per step/runAgents are expensive — you must see spend per task
Latency per spanFind the slow step (usually a tool or a big LLM call)
Success / failure + typeClassify failures (your taxonomy!) to fix the common ones
Trajectory replayReproduce a bad run exactly to debug non-determinism
YOUR work — you're AHEAD here: your observability/tracer.py already does per-node latency, token/cost, a failure taxonomy (FailureType), and run summaries. That's a production observability layer most candidates have never built. Tools that do this commercially: LangSmith, Langfuse, OpenTelemetry.

6. The golden rule of agent logging

Never log secrets or raw PII. Traces capture prompts — which may contain keys, tokens, or user data. Scrub before persisting. (Ties directly to Secrets Hygiene + OWASP LLM02 Sensitive Information Disclosure.)

7. Eval + Observability = the flywheel

production traces ──▶ find failures ──▶ add to golden dataset ▲ │ └──── ship fix ◀── eval passes ◀── fix + regression test
Founder flywheel: observability surfaces real failures → they become eval cases → fixes are regression-tested → you ship with confidence. This loop is the difference between a demo and a product.

8. Q&A Drills

How do you evaluate a non-deterministic agent?
On multiple axes: final-output quality (LLM-as-judge against a rubric), trajectory (did it call sensible tools), task success (goal checker), and components (RAGAS for retrieval). Against a golden dataset, run as a regression suite on every change, averaging over multiple runs to handle variance.
What are LLM-as-judge pitfalls?
Position bias, verbosity bias, self-preference, and score variance. Mitigate by randomizing order, tight rubrics, averaging multiple runs, and calibrating against human labels.
What do you trace in an agent and why?
Per-span: tokens, cost, latency, tool name/args/result, and the decision made. Per-run: totals, success/failure with a failure-type classification, and full trajectory for replay. Because agents are costly and non-deterministic, you can't debug or control them without this.
Biggest logging risk in observability?
Leaking secrets/PII — traces capture prompts that may contain keys or user data. Scrub before persisting. It maps to OWASP LLM02 Sensitive Information Disclosure.
