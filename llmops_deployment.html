3. FastAPI — The Standard for LLM API Serving

Why FastAPI (not Flask, not Django)

• Async native: LLM calls are I/O bound (waiting for Groq/OpenAI response). Async = handle 100 concurrent requests with 1 worker.

• Auto-generated docs: Visit /docs → instant Swagger UI. YOUR API is self-documenting.

• Pydantic validation: Request/response schemas enforced automatically. Bad input rejected with clear error.

• Streaming support: SSE (Server-Sent Events) for token-by-token output built-in.

• Industry standard: Used by Anthropic, LangChain, most AI startups. Interviewers expect this.

Production FastAPI patterns for LLM apps

1. Lifespan (load model once at startup, not per request):

@asynccontextmanager
async def lifespan(app):
  app.state.model = SentenceTransformer('all-MiniLM-L6-v2') # 3s once
  yield # app runs
  # cleanup on shutdown

2. Health endpoint (required by every cloud platform):

@app.get("/health")
async def health():
  return {"status": "healthy", "model_loaded": True}

3. Pydantic models (type-safe request/response):

class ScoreRequest(BaseModel):
  title: str = Field(min_length=3, max_length=200)
  description: str = Field(default="", max_length=5000)

4. Error handling (don't crash, return useful errors):

@app.exception_handler(Exception)
async def global_handler(request, exc):
  return JSONResponse(status_code=500, content={"error": str(exc)})

4. Docker — Ship Anywhere, Run Everywhere

📦 Analogy: Shipping Container

Before shipping containers: every cargo needed custom handling. Fragile, slow, expensive.

After containers: ANY cargo fits in a standard box. Load on ANY ship. Unload at ANY port. Standard interface.

Docker = shipping containers for software. Your app + all dependencies in one standard box. Runs identically on your laptop, CI, and cloud.

Dockerfile anatomy for LLM apps
# Multi-stage build (smaller final image)
FROM python:3.12-slim
WORKDIR /app

# Install deps (cached layer — only rebuilds if requirements change)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copy app code
COPY . .

# Pre-download model INTO image (fast startup!)
RUN python -c "from sentence_transformers import SentenceTransformer; SentenceTransformer('all-MiniLM-L6-v2')"

# Security: don't run as root
RUN useradd appuser && chown -R appuser /app
USER appuser

EXPOSE 8000
HEALTHCHECK CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

Key decisions: (1) Pre-download model = 2s startup not 30s. (2) Non-root user = security. (3) HEALTHCHECK = cloud knows when container is ready. (4) Slim base = 400MB not 2GB.

Docker commands you need to know
# Build
docker build -t job-scorer-api:v1 .

# Run locally

# Push to registry (for cloud deploy)

5. Cloud Deployment Options

GCP Cloud Run

RECOMMENDED FOR YOU

What: Serverless containers. Push Docker image → get URL. Auto-scales 0→N.
Cost: ₹0 when idle (scales to zero). Free tier: 2M requests/month.
Deploy: gcloud run deploy — one command!
Best for: APIs with variable traffic (like your job scorer).

AWS Lambda

What: Serverless functions. No containers needed (but supports them).
Cost: Pay per invocation. Free tier: 1M requests/month.
Best for: Event-driven (your GitHub Actions trigger style). Cold starts can be slow for ML models.

AWS EC2 / GCP Compute

What: Full virtual machines. You manage everything.
Cost: Pay per hour regardless of traffic. Cheapest for constant load.
Best for: Self-hosted vLLM, models that need GPU 24/7.

Railway / Render

What: Simplified PaaS. Push git → auto-deploy. Like Heroku but modern.
Cost: $5-20/month for always-on. Easier than GCP/AWS.
Best for: Portfolio demos where you want simple + reliable.

Cloud Run deploy (5 commands — do this for real)
# 1. Auth
gcloud auth login
gcloud config set project YOUR_PROJECT

# 2. Build + push (cloud builds it for you!)
gcloud builds submit --tag gcr.io/YOUR_PROJECT/job-scorer:v1

# 3. Deploy
gcloud run deploy job-scorer \
  --image gcr.io/YOUR_PROJECT/job-scorer:v1 \
  --region asia-south1 \
  --allow-unauthenticated \
  --memory 1Gi --cpu 1 \

# 4. Get URL
gcloud run services describe job-scorer --format='value(status.url)'
# → https://job-scorer-xxx-el.a.run.app ← LIVE API!

That's it. You now have a LIVE production API. ₹0 cost at idle. Auto-scales. This is a real resume line.

6. CI/CD for LLM Apps (Beyond Regular DevOps)

Prompt Regression Tests (the KEY LLMOps addition)

Regular code has unit tests. LLM apps need PROMPT tests:

# test_prompts.py — runs in CI before deploy
TEST_CASES = [
  {"input": "AI Engineer Chennai", "expect_tier": "Strong", "expect_score_min": 70},
  {"input": "Java Developer Pune", "expect_tier": "Weak", "expect_score_max": 40},
]

def test_scoring_accuracy():
  correct = 0
  for case in TEST_CASES:
    result = score(case["input"])
    if result["tier"] == case["expect_tier"]:
      correct += 1
  accuracy = correct / len(TEST_CASES)
  assert accuracy >= 0.8, f"Prompt accuracy dropped to {accuracy}!"

This blocks deployment if a prompt change degrades quality. It's the LLMOps equivalent of "tests must pass before merge."

7. Streaming (Token-by-Token Delivery)

📺 Analogy: Netflix vs YouTube Download

Non-streaming: Wait for entire movie to download before watching. (Wait 5 seconds for full LLM response.)

Streaming: Start watching immediately while it downloads. (See tokens appear one by one as LLM generates.)

Users perceive streaming as 10x faster even though total time is the same. It's a UX game-changer.

SSE (Server-Sent Events) — How streaming works
from fastapi.responses import StreamingResponse

@app.post("/chat/stream")
async def chat_stream(request: ChatRequest):
  async def generate():
    stream = groq.chat.completions.create(
      model="llama-3.3-70b-versatile",
      messages=request.messages,
      stream=True # ← THIS enables streaming
    )
    for chunk in stream:
      token = chunk.choices[0].delta.content or ""
      yield f"data: {token}\n\n" # SSE format
    yield "data: [DONE]\n\n"
  return StreamingResponse(generate(), media_type="text/event-stream")

Client side (browser):

const source = new EventSource("/chat/stream");
source.onmessage = (event) => {
  document.getElementById("output").innerText += event.data;
};

8. Prompt & Model Versioning

The Problem: "Which prompt was in production when quality dropped?"

Without versioning, you change a prompt → quality drops → you can't REMEMBER what the old prompt was. This is like coding without git.

Solution: Prompt Registry pattern

PROMPTS = {
  "scorer_v1": {"template": "...", "model": "llama-3.3-70b", "metrics": {"accuracy": 0.78}},
  "scorer_v2": {"template": "...", "model": "llama-3.3-70b", "metrics": {"accuracy": 0.85}},
}
ACTIVE = "scorer_v2" # change this to switch versions instantly

Better: LangFuse prompt management — change prompts WITHOUT redeploying code. Rollback in 1 click. A/B test by routing % of traffic.

Model versioning (handle deprecations gracefully)

YOU already learned this the hard way: Groq decommissioned llama-3.1-70b-versatile mid-project.

Pattern: Never hardcode model names in business logic. Use a settings layer:

MODEL_ROUTING = {
  "fast": "llama-3.1-8b-instant",
  "default": "llama-3.3-70b-versatile",
  "creative": "llama-3.3-70b-versatile",
}
# Change ONE place to switch models globally

YOUR settings.py already does this with model_fast and model_default! Good pattern.

9. Scaling Patterns

Semantic Caching

What: If similar query was answered before (cosine > 0.95), return cached answer. Skip LLM entirely.
Savings: 30-50% of LLM calls for repetitive queries (support bots, FAQ).
How: Embed query → search cache collection → if match → return cached response.

Model Routing (Tiered)

What: Route simple queries to cheap/fast model, complex to expensive/smart model.
How: Classifier decides complexity → route to 8B (₹cheap) or 70B (₹expensive).
YOUR pattern: You could score jobs with 8B (fast, free) and only use 70B for borderline cases.

Rate Limiting

What: Prevent abuse. Max 10 requests/minute per user.
How: Redis counter per API key. Reject with 429 if exceeded.
Why: Without this, one user can burn your entire token budget in minutes.

Async + Queue (Background Jobs)

What: Heavy tasks (video generation) run in background. API returns immediately with job ID.
How: Redis queue (Celery/RQ) + webhook callback when done.
YOUR use: ContentMind video assembly could be a queued job that notifies via Telegram when done.

Circuit Breaker

What: If Groq API fails 3 times in a row → STOP calling for 60 seconds. Serve degraded response instead.
Why: Prevents cascading failures. Your user gets "I'm temporarily limited" instead of 500 errors.
YOUR code: Your Groq rate limit tracking is a basic version of this!

Auto-Scaling

What: Cloud Run spins up more instances when traffic spikes. Scales back to 0 when idle.
Config: --min-instances 0 --max-instances 10
Cost: Pay only for actual compute used. ₹0 when nobody is calling your API.

10. Monitoring & Observability in Production

The 5 Metrics Every LLM API Must Track

1. Latency (p95): 95th percentile response time. Target: <3 seconds. Alert if >5s.

2. Error rate: % of requests returning 5xx. Target: <2%. Alert if >5%.

3. Token usage: Tokens consumed per request. Track for cost forecasting.

4. Quality score: LLM-as-judge on sampled responses. Alert if average drops >5%.

5. Cost per request: (Input tokens × input price + output tokens × output price). Track daily spend.

Structured Logging (JSON format for searchability)
import logging, json
logging.basicConfig(format='{"time":"%(asctime)s","level":"%(levelname)s","msg":"%(message)s"}')

# Every LLM call logs:
log.info(json.dumps({
  "event": "llm_call",
  "model": "llama-3.3-70b",
  "tokens_in": 680,
  "tokens_out": 120,
  "latency_ms": 2300,
  "cost_usd": 0.0008,
  "success": True

JSON logs → queryable in Cloud Logging / Datadog / Grafana. "Show me all requests where latency > 5s" becomes a simple query.

12. Interview Answers

Q: "How would you deploy an LLM application to production?"

"I'd serve it via FastAPI with async endpoints, Pydantic validation, and health checks. Containerize with Docker (multi-stage build, pre-downloaded models, non-root user). Deploy to GCP Cloud Run for serverless scaling (0 to N instances, pay-per-use). CI/CD via GitHub Actions with prompt regression tests as a quality gate — blocks deploy if accuracy drops below 80%. Add LangFuse for tracing and cost monitoring. For high traffic: semantic caching to skip 30-50% of LLM calls, and model routing to use cheap 8B for simple queries."

Q: "How do you handle model deprecation in production?"

"Never hardcode model names in business logic — use a settings/routing layer. When Groq deprecated llama-3.1, I had fast-fail detection: if the error contains 'decommissioned', raise immediately without retrying. The fix was changing one string in settings.py. For production: I'd add a fallback chain (primary model → secondary → cached responses) so the system degrades gracefully while the team updates."

Q: "How do you optimize cost in LLM production systems?"

"Five layers: (1) Semantic caching — skip LLM for similar past queries (30-50% savings). (2) Model tiering — route simple tasks to 8B, complex to 70B. (3) Prompt optimization — shorter prompts = fewer tokens (I reduced 12 calls to 5, saving 60%). (4) Batch processing — batch multiple items into one LLM call where possible. (5) Token budgets per request — hard cap prevents runaway costs. In my pipeline, these combined achieve ₹0/month running cost."
