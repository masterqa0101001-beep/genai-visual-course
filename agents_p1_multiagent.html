🕸️ P1 — Multi-Agent Orchestration

From "one agent" to "a system of agents." The headline 2026 skill. Founder-level: patterns, tradeoffs, and the failure modes that make multi-agent dangerous.

⭐ THE SENTENCE THAT SIGNALS SENIORITY

"Multi-agent systems have the same complexity as microservices — compounded by non-determinism. I only add agents when a single agent hits a specific ceiling it can't overcome. More agents is more cost, more latency, and more ways to fail — not automatically more capable."

1. When to go multi-agent (and when NOT to)

This is the gate. Anthropic + the LangGraph production community agree: start with one agent. Reach for multi-agent only when you hit a real ceiling:

Go multi-agent when…Stay single-agent when…
One agent's context is overflowing with too many toolsA handful of tools fit comfortably
Distinct expertise needs distinct prompts (SEO vs legal vs code)One role covers the task
Subtasks genuinely parallelizeWork is inherently sequential
You need independent verification (one agent checks another)Self-check is good enough
The trap: multi-agent feels impressive but multiplies cost (N agents = N+ LLM calls per step), latency, and debugging pain. Non-determinism compounds — agent A's slightly-wrong output becomes agent B's input.

2. The 4 core patterns

① Supervisor (Router + Workers)

┌──────────────┐ task ───▶│ SUPERVISOR │ (its ONLY job: route) └──┬───┬───┬────┘ ┌─────┘ │ └─────┐ ┌───▼──┐ ┌───▼──┐ ┌───▼──┐ │Worker│ │Worker│ │Worker│ │ A │ │ B │ │ C │ └───┬──┘ └───┬──┘ └───┬──┘ └─────────┼─────────┘ ▼ SUPERVISOR merges → done?

A central LLM owns routing, state merging, and failure decisions. Each worker handles one bounded subtask and returns control. Most accurate because routing is a dedicated, focused LLM call. LangGraph: create_supervisor() wraps specialists into a routing graph via handoff tools.

YOUR work: your content_router.py (story vs tech) is a supervisor. Your quality council (critic/fact-check/SEO under a moderator) is supervisor + parallelization.

② Swarm (peer-to-peer handoffs)

Agent A ──handoff──▶ Agent B ──handoff──▶ Agent C ▲ │ └────────────── handoff ─────────────────┘ (no central router — last active agent drives next step)

Agents hand off directly to each other, no central supervisor. Faster (skips the routing hop) but more misroute-prone.

Supervisor vs Swarm — the founder tradeoff: Supervisor = more accurate (dedicated router) but one extra LLM call per hop. Swarm = faster but routing errors creep in. Choose based on whether your bottleneck is latency (swarm) or misroutes (supervisor).

③ Planner-Executor

goal → [PLANNER] → [step1, step2, step3, step4] │ │ │ │ [exec][exec][exec][exec] │ [REPLANNER] (adjust remaining steps)

A planner writes the whole plan up front; executors run each step; a replanner adjusts based on results. Cheaper + more predictable than re-reasoning every step.

④ Debate / Voting

Multiple agents independently judge, then aggregate (vote or moderator synthesis). Great for high-stakes evaluation where multiple perspectives raise confidence.

3. Handoffs — the hard part nobody teaches

A handoff is where multi-agent systems corrupt state. The production rule:

A handoff should carry only:
  • ✅ validated state (not raw, unchecked output)
  • ✅ the next objective + constraints
  • ✅ an audit ID (trace which agent did what)
  • ❌ NOT the entire conversation history by default (cost + leakage)
Keep identifiers consistent with your thread / session / user-isolation model, or you leak one user's state into another's.
Failure mode — disagreement: when two agents disagree, who wins? The supervisor must own that decision explicitly, or the system loops or deadlocks. Design the tiebreaker up front.

4. State management across agents

Founder-grade multi-agent needs externalized, persisted state (Redis/Postgres), so any worker/pod can resume a session. In LangGraph: a shared state object + checkpointer, with the Send API for fan-out parallelism.

5. Founder economics of multi-agent

DimensionReality
CostEach agent + the router is its own LLM call. A 3-agent supervisor loop can be 4–6× a single agent per step.
LatencySupervisor adds a routing hop; swarm skips it. Parallelize independent agents to claw back time.
DebuggabilityNon-determinism × N agents. You MUST have tracing (next lesson) or you're flying blind.
ReliabilityErrors compound. Validate state at every handoff.
SecurityMore agents = more identities to scope. Each should have least-privilege tools (ties to agentic security).
Company-building insight: the best multi-agent systems look boring — a supervisor, 2–3 focused workers, validated handoffs, strong tracing. Resist "agent swarm" hype; sell reliability.

6. Q&A Drills

Supervisor vs swarm — when do you pick which?
Supervisor when accuracy/correct routing matters most — routing is a dedicated focused LLM call. Swarm when latency is the bottleneck — agents hand off peer-to-peer, skipping the router hop, at the cost of more misroutes.
What should a handoff carry between agents?
Only validated state, the next objective + constraints, and an audit ID — not the full conversation by default. Passing raw unvalidated output or the whole history causes state corruption, cost blowup, and cross-session leakage.
When would you NOT use multi-agent?
When a single agent handles it. Multi-agent has microservice-level complexity plus non-determinism. I only add agents at a specific ceiling — context overflow from too many tools, genuinely distinct expertise, real parallelism, or needing independent verification.
How do you handle two agents that disagree?
The supervisor owns the tiebreaker explicitly — defined up front. Without that, the system loops or deadlocks. State merging and failure decisions are the supervisor's job, not an emergent accident.
