🤖 P0 — Core Agent Mechanics

Founder-level. Not "how to call a framework" — but what an agent actually is, when it breaks, what it costs, and how you'd architect it for a company. Sourced from Anthropic's "Building Effective Agents" + mapped to YOUR ContentMind pipeline.

⭐ THE ONE SENTENCE THAT MAKES YOU SOUND LIKE A FOUNDER

"An agent is just an LLM running tools in a loop based on environmental feedback — everything else is a framework trying to sell you abstraction. The hard part isn't the loop, it's the tool interface, the stopping conditions, and the cost of being wrong."

1. The Mental Model: Workflow vs Agent

Anthropic draws the single most important architectural line in this entire field. Memorize it — interviewers and co-founders both test it:

WorkflowAgent
LLMs + tools orchestrated through predefined code pathsLLM dynamically directs its own process and tool use
Predictable, cheap, debuggableFlexible, expensive, can compound errors
Use when the task decomposes cleanlyUse when you can't predict the steps in advance
The founder insight: Most "AI agent" startups are actually building workflows and calling them agents for the hype. Knowing the difference means you build the cheaper, more reliable thing when you can — and only pay the agent tax when flexibility genuinely earns it.
Anthropic's rule, verbatim intent: "Find the simplest solution possible, and only increase complexity when needed." Sometimes the right answer is not building an agent at all — a single LLM call with retrieval + good examples is often enough.

2. The Loop — Think → Act → Observe

This is the heartbeat. Everything (LangChain, LangGraph, CrewAI, AutoGen) is this loop plus decoration.

USER GOAL │ ▼ ┌──────────────┐ │ THINK │ LLM reasons over (history + tools + goal) └──────┬───────┘ ▼ ┌──────────────┐ │ ACT │ parse decision → call ONE tool └──────┬───────┘ ▼ ┌──────────────┐ │ OBSERVE │ feed tool result back into history └──────┬───────┘ ▼ Done? ──No──┐ (loop back to THINK) │ │ Yes └──────────────┘ ▼ FINAL ANSWER / stop condition (max steps hit)

The 50-line truth (your module_4 code)

messages = [system_prompt, user_goal]
for step in range(MAX_STEPS):            # ← stopping condition #1
    thought = llm(messages)              # THINK
    action, args = parse(thought)        # DECIDE
    if action == "final_answer":         # ← stopping condition #2
        return args
    if action not in TOOLS:              # ← guardrail: hallucinated tool
        messages.append("Invalid tool"); continue
    result = TOOLS[action](args)         # ACT
    messages.append(result)              # OBSERVE
YOUR work mapped: Your trend_ranker.py is this exact loop (ReAct). Your main_pipeline.py wraps it in LangGraph. When an interviewer asks "how does your pipeline work under the hood," you point at this loop — not at add_node().

3. The 5 Workflow Patterns (Anthropic's building blocks)

Before you reach for a full agent, these composable patterns solve most real problems. Each is a tool in your founder toolbox.

① Prompt Chaining

In → [LLM 1] → gate? → [LLM 2] → [LLM 3] → Out │ fail → stop

Decompose into fixed steps; each LLM call does one easy thing. Add programmatic gates between steps. Use when the task splits cleanly and you'd trade latency for accuracy.

② Routing

Classify the input, send it to a specialized path. Use when distinct categories are better handled by different prompts/models. Founder move: route easy queries to a cheap model (Haiku) and hard ones to a strong model (Sonnet) — this is a direct cost lever.

YOUR work: content_router.py (story vs tech mode) is exactly this.

③ Parallelization (Sectioning + Voting)

Sectioning: split independent subtasks, run concurrently. Voting: run the same task N times for confidence. Use when you need speed or multiple perspectives (e.g. one model answers, another screens for safety).

YOUR work: your quality council (critic / fact-check / virality / SEO) is the Voting pattern.

④ Orchestrator-Workers

┌─ ORCHESTRATOR (LLM breaks down task) │ ├──→ Worker LLM (subtask A) │ ├──→ Worker LLM (subtask B) │ └──→ Worker LLM (subtask C) └─ synthesize results

Like parallelization, but subtasks are decided at runtime by the orchestrator, not pre-defined. Use when you can't predict how many sub-tasks you'll need (e.g. "edit however many files this bug touches").

⑤ Evaluator-Optimizer

One LLM generates, another critiques, loop until good. Use when you have clear eval criteria and iteration measurably helps (translation, deep search).

⭐ FOUNDER DECISION TREE

Can a single LLM call + retrieval do it?        → DO THAT (cheapest)
Task splits into fixed steps?                   → Prompt Chaining
Distinct input types?                           → Routing
Independent subtasks / need confidence?         → Parallelization
Can't predict the subtasks?                     → Orchestrator-Workers
Clear eval criteria + iteration helps?          → Evaluator-Optimizer
Truly open-ended, unknown # of steps, trusted?  → AGENT (pay the tax)

4. The Augmented LLM (the atom)

Every pattern is built from one atom: an LLM augmented with retrieval + tools + memory. The model generates its own search queries, picks tools, and decides what to remember.

┌─────────────────────────┐ ───────│ AUGMENTED LLM │─────── query │ ┌────────┬────────┬────┐ │ output │ │Retrieval│ Tools │Mem │ │ │ └────────┴────────┴────┘ │ └─────────────────────────┘
MCP connection: Anthropic says one clean way to wire these augmentations is the Model Context Protocol — the standard that lets your agent plug into a growing ecosystem of tools. (That's your P1 topic, and you've already built an MCP server — huge edge.)

5. Tool Design — the ACI (where founders win or lose)

Anthropic's sharpest practical lesson: invest as much effort in your Agent-Computer Interface (ACI) as teams invest in human UI. On their SWE-bench agent, they spent more time optimizing tools than the prompt itself.

Tool design rules that actually move the needle

  • Give the model room to "think" before it commits to a format (don't force it to write itself into a corner).
  • Match formats to what the model saw on the internet — markdown over escaped-JSON-with-newlines.
  • Remove overhead — e.g. don't make it count line numbers for a diff.
  • Poka-yoke (mistake-proof) your tools — Anthropic switched to absolute file paths and the model stopped making path errors entirely.
  • Write tool descriptions like a docstring for a junior dev — include example usage, edge cases, boundaries vs other tools.
#1 failure mode in production: ambiguous tool descriptions → wrong tool selection. The fix is not a smarter model, it's a clearer interface. This is a cheap, high-leverage thing most teams skip.

6. Stopping Conditions & Control (the part amateurs forget)

Agents operate for many turns and you must retain control. Three levers:

  1. Max iterations — hard cap so a confused agent can't loop forever (or bankrupt you).
  2. Explicit final_answer — the agent signals completion.
  3. Ground truth every step — tool results / code execution tell the agent (and you) real progress, not vibes.
The autonomy tax: Anthropic is explicit — agent autonomy means higher cost and compounding errors (one bad step poisons the next). Their guidance: test extensively in sandboxed environments with guardrails before trusting autonomy.

7. Founder-Level Economics & Scale

⭐ THE THINGS A FOUNDER KNOWS THAT A CANDIDATE DOESN'T

DimensionWhat you must reason about
Cost per taskEvery loop step = 1+ LLM call. A 10-step agent at Sonnet prices can cost 20–50× a single call. Route cheap models for easy steps.
LatencySequential loops feel slow. Parallelize independent work; stream partial output.
Blast radiusAn autonomous agent with a delete or send_money tool is a liability. Least privilege + human gates.
ReliabilityNon-determinism means you need evals + regression tests, not "it worked once."
Trust boundaryTrusted env = more autonomy OK. Untrusted inputs (web, user content) = assume adversarial.
Company-building takeaway: The successful teams Anthropic worked with used simple composable patterns, not complex frameworks. If you start a company, your moat is a clean tool interface + great evals + cost discipline — not which framework you picked.

8. Interview / Co-founder Q&A Drills

What's the difference between a workflow and an agent?
A workflow runs LLMs through predefined code paths — predictable and cheap. An agent lets the LLM dynamically control its own process and tool use — flexible but costly and error-prone. I default to workflows and only use agents when the step count is genuinely unpredictable.
How do you stop an agent from looping forever / blowing the budget?
Hard max-iteration cap, an explicit final_answer action, and ground-truth checks each step. Plus repeated-action detection and a spend cap. Autonomy without stopping conditions is how you get a $10k API bill.
You have a flaky agent picking the wrong tool. What do you fix first?
The tool interface, not the model. Rewrite descriptions like a docstring for a junior dev, add example usage and edge cases, and poka-yoke the arguments (e.g. absolute paths). Anthropic spent more time on tools than prompts for a reason.
When would you NOT build an agent?
When a single LLM call with retrieval and good in-context examples solves it. Agents trade latency and cost for flexibility — if the task decomposes cleanly, a workflow or even one call is the right, cheaper engineering choice.
